# 播放可靠性与性能约束

## 播放与故障恢复

- 用户选择频道、集数或线路时重置整组线路的重试预算；内部自动恢复不可无限循环。
- 播放失败按循环顺序尝试尚未试过的线路，包括回到第一条；所有线路耗尽后停止播放并保留错误信息。
- 播放进度卡住时当前资源仅重试一次，然后尝试下一线路。对已保存的点播进度，切线时保留上次可靠位置；直播始终回到直播边缘。
- Media3 的 `BEHIND_LIVE_WINDOW` 在一分钟窗口内最多内部恢复一次；重复失败交给资源恢复策略。
- MPV 只在 Android Surface 已建立且开始载入文件后启动加载超时；零进度直播可通过播放恢复事件标记就绪。
- 播放暂停期间停止加载与卡顿计时；恢复后即使进度未改变，也重新武装卡顿监控。

## 内存及网络

- MPV demuxer 缓存上限为 64 MiB，后向缓存为 16 MiB；优先保障低内存机顶盒。
- ResourceProbe 对相同资源的并发请求只发起一次网络测速，仍允许两个不同资源并行请求。
- 影视聚合通过已知外部 ID 和别名索引缩小候选集合，严格验证所有成员的匹配关系。
- XMLTV 的单来源映射在未变化时被复用，减少多源渐进加载期间的数据复制及正则重复编译。
- 网络二进制测速仅解码前 2 KiB 判断协议，真正解析 HLS 时才解码完整播放列表样本。

## 验证与边界

执行 `./gradlew :media:test :app:testDebugUnitTest :app:lintDebug :app:connectedDebugAndroidTest`。
CI 覆盖 API 24 和 API 34；尚需真实电视硬件验证 HLS、RTSP、组播、不同芯片硬解与 MPV 表面重建。
运营商 UDP/RTP 组播是否可用取决于网络与播放器后端，不能只靠 M3U 地址解析保证兼容。
